# The model is the public resource, and the request names its area

## Status

accepted

Implements D11, D16, D17, D18 and D19 of the Forti point-plane plan. Consumes
core's ADR 0028 (plugins contribute routes under `/api/`) and ADR 0029 (one
opt-in proxy cache for `/api/`), and depends on ADR 0027's amendment for the
instance-wide publication root.

**Supersedes core's `docs/adr/0028-a-serving-pair-per-organisation.md`**, which
exists only on the abandoned branch `feat/forti-serving` (`bc94464`). That number
now belongs to core's plugin URL hook, and this is the plugin's own ADR because
the whole serving plane is the plugin's (D19). What that document decided —
a `rawdataforecaster` + `jsonfrontend` pair per organisation, generated by
`manage.py generate_forti_compose`, dialled at a hostname derived from the
organisation slug — is reversed here in every part except the shape of the view.

## Context

Serving a point forecast means asking `jsonfrontend`, which asks
`rawdataforecaster`, which answers from whichever gridpoint is nearest. The
question this ADR answers is **which data a request is allowed to be answered
from**, and where that is enforced.

### The old answer was the process, and the fork removed the need for it

`bc94464` reasoned that `rawdataforecaster`'s gRPC surface carried no area field,
so `bestArea` walked every dataset the process held and returned the globally
nearest gridpoint. A process holding two organisations' areas did not *risk*
answering across tenants; it did so as arithmetic, silently, and the more readily
the closer the two areas were. The only isolation available was **which process
is asked**, which meant one pair per organisation, which meant generating the
compose file, which meant `forti-jsonfrontend-{slug}` — a name derived from an
immutable validated DNS label so that the generator and the view could not drift
apart.

M5.1's fork (`wmo-raf/forti`, `develop`) gives `GetForecastRequest` a repeated
`areas` filter and reports the answering area back as `ForecastMeta.area` →
`properties.meta.area`. D14 therefore runs **one pair for the instance**, and
this route is what replaces the process boundary.

### Three facts about the reader that the design has to fit

**An empty area filter is not "no areas".** proto3 decodes an absent repeated
field to a nil slice, and `selects` reads an empty filter as no narrowing at all
— so a request that forgets its area is answered from every organisation's
areas. The filter can only ever narrow, never widen, which is exactly why the
one thing that must not happen is *sending nothing*.

**The 404 branch became reachable, and it now means something different.**
`WithinGeographicArea` (`dataset.go:196`) returns true unconditionally when no
polygon is configured, and GeoRiva writes no `geographic_extent`, so "outside the
grid" is unreachable. But `bestArea` fails closed when every *named* area is
missing from `f.datasets`, and that also surfaces as `ErrOutsideAllGrids` →
`http.Error(404, "Outside of coverage area")`. With exactly one area named, a
404 can only mean the area we asked for is not loaded.

**The one successful response that names no area is the coverage error.**
`EncodeError` (`encode.go:30`) builds its metadata from scratch — an `error`
string, an empty `units` map, an empty `timeseries` — and never sets `Area`,
because no dataset answered. Every real forecast names one.

### And one about the instance

Core has `DEFAULT_AUTHENTICATION_CLASSES` and nothing else in `REST_FRAMEWORK`.
There is no `DEFAULT_THROTTLE_RATES`, this is the first throttled route, and D19
forbids adding a Forti-shaped key to core's settings.

## Decision

### The model is the resource

`GET /api/forecast/{model}/?lat=&lon=`, model required, plus
`GET /api/forecast/` listing the models the caller may see. `{model}` is
`FortiPublication.slug`, prefilled from `catalog.slug` and immutable once
published.

The alternative — `/api/forecast/?lat=&lon=`, with the organisation in the host
choosing the data — is what `bc94464` had, and it only works while an
organisation has exactly one area. D16 forbids blending, so a consumer has to be
able to say which model it wants, and the name it says is a public contract
rather than an internal id.

### Exactly one area, and the empty case is unreachable rather than unlikely

There is one function that builds an upstream query, `upstream_params`, and it
**raises before the socket** on a falsy area. It raises `RuntimeError` and
nothing catches it: an omitted area is an instance bug, and a 500 is the honest
report of one, where a 4xx would file it under "the caller did something wrong".

Nothing else is forwarded — an allowlist, not a passthrough. `area` and
`topography` from the caller are refused with a **400** rather than dropped,
because they are the two parameters that change which data answers and a caller
who sent one believes it did something.

### `properties.meta.area` is checked for equality on every response

Not membership (D16: one request names one area, so anything else answering is a
fault whatever it is), and not "if present": a document carrying a `timeseries`
must name our area or it is a **502** with an ERROR log. The single exception is
the coverage-error body, which carries no forecast data and no area.

### Visibility is one query, asked by both routes

`FortiPublicationQuerySet.visible_to`, mirroring `CollectionQuerySet.visible_to`
and asking core's own `visible_visibilities` — so the audience rule here is the
same function the STAC API and the dataset pages ask, not a second copy of it.
`servable_models()` wraps it in `scoped_queryset` and is called by the listing
*and* by the detail route, because D18's rule has two halves that must agree: a
model the caller may not see is **absent** from the listing and **404s**
directly, so the endpoint cannot enumerate what a tenant publishes. Two filters
at two call sites is the arrangement in which one is later narrowed and the other
is not, and the drift is silent in the direction that matters.

**Both tiers are read, the publication's and the collection's.** `clean()`
already refuses a publication more open than its collection, but it runs when the
*publication* is saved; narrowing the collection afterwards is an ordinary edit
by somebody with no reason to know a Forti publication exists.
`effective_visibility` is the narrower of the two and is what the response
marking and the listing report.

The query also requires `published_version IS NOT NULL` and an active collection
and catalog, which makes the served set a strict **subset** of the area list
`rdfconfig.servable` builds. The subset direction is the safe one: a reader
holding an area nothing serves is wasted memory, while a route serving an area no
reader holds is a 503.

### The throttle is a `SimpleRateThrottle` with a rate this plugin owns

`ScopedRateThrottle` was the obvious base class and it is wrong here twice.

Its whole mechanism is to look the rate up in
`REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"][scope]`, which core does not have;
`get_rate()` raises `ImproperlyConfigured` on a missing scope, so the first
request to reach the counter would have been a 500. Adding the key to core's
settings is what `bc94464` did and what D19 forbids.

Worse, `ScopedRateThrottle.allow_request` overwrites `self.scope` from
`getattr(view, "throttle_scope", None)` and **allows the request unconditionally
when it is unset**. `bc94464`'s view declared no `throttle_scope`, so its throttle
never throttled anything — while its unit test passed, because the test
constructed a fake view that had the attribute. A control that silently does
nothing is worse than no control.

So: `scope` is a class attribute, `get_rate()` reads
`GEORIVA_FORTI_FORECAST_THROTTLE_RATE` with a plugin default of **60/min**, and
`None` disables it for an operator who rate-limits at their own edge. Sixty a
minute is one point forecast a second sustained, per caller per organisation;
more than that is a coordinate sweep, and a public model's repeat traffic is
served by the proxy and never counted. The organisation is part of the cache key
because `SimpleRateThrottle` keys anonymous callers on IP alone, and two tenants
behind one NAT would otherwise share a bucket.

### Only a successful public-model response is marked shareable

`Cache-Control: public, max-age=1800` on a 200 from a model whose
`effective_visibility` is public; `private, no-store` when it is not; `no-store`
on every error. The `/api/` cache key is `$host$request_uri` and **carries no
identity** (ADR 0029), so `public` means "serve this to whoever asks next on this
host" and nothing weaker.

1800 is met.no's production `data_expiry_offset` (plan §6), used as the analogous
hint — and deliberately **not** wired to `jsonformat.DATA_EXPIRY_OFFSET`, which is
a different quantity ("seconds after a run's last timestep") that happens to have
been given the same value. Coupling them would mean tuning an expiry hint
silently changed how long a proxy holds a document. The data changes once per run
at best, so half an hour of sharing costs a consumer nothing they would notice.

**The listing is never marked public**, though most of its callers are anonymous
and would receive a document that is safe to share. It varies by audience at a
URL that carries none, and what would keep a member's listing out of the shared
cache is nginx's `proxy_no_cache` on the session cookie — resting on that is
exactly the "correctness depends on having enumerated every credential transport"
that ADR 0029 refuses. The saving is one queryset.

### Upstream statuses map by who is at fault

| upstream | this route | why |
|---|---|---|
| unreachable | 503 | no pair, or one that is down. Not the caller's fault and not fixable by them |
| 5xx | 503 | same |
| 404 | 503 + ERROR | the area we named is not loaded — see below |
| any other non-200 | 502 + ERROR | every parameter the reader saw was ours |
| 200 that will not parse | 502 + ERROR | jsonfrontend answers a forecast or `http.Error` prose, never both |
| 200 naming another area | 502 + ERROR | the tenant check |
| 200 | passed through unchanged | including the coverage-error body |

The 404 is the interesting one. It reads "Outside of coverage area", and passing
it through would blame the caller's coordinates — but with one area named and no
`geographic_extent` written, it can only mean that area is not resident. That is
a real state and M5.9 has to clear it: the live row's `published_version` is set
under the superseded `central/forti/` layout, so `refresh_forti_config` names an
area whose bytes are not under `_forti/`, and the pair comes up holding nothing.
503 says "this model is not currently being served", which is both true and the
thing an operator needs to see.

Every branch switches on the status code and on whether the body parses —
**never on `Content-Type`**. jsonfrontend sets none on success, so Go's sniffing
stamps `text/plain; charset=utf-8` on a perfectly good locationforecast document,
and a view that trusted the header would send every real forecast down an error
branch.

### What the listing says about a model

`model`, `title`, `visibility`, `bbox`, `reference_time`, `parameters` — what
somebody choosing a model or checking coverage has to know, and nothing else.

`title` is the **catalog's** name because the slug is the catalog's slug: D17's
reason for prefilling from it is that `Catalog` is already the thing a consumer
would call a model, so the name and the name it is asked by come off one object.
`parameters` is translated into locationforecast's vocabulary, because
`published_parameters` holds forti's *internal* names (`air_temperature_2m`)
which appear nowhere in the document a consumer reads.

Absent on purpose: the version, the grid id, the point and step counts, the build
status, the collection and catalog slugs, the organisation. Those answer "is the
pipeline healthy", which is the verification panel's question (D23) and an
operator's, not a consumer's.

## Alternatives considered

**Keep the tenant boundary in the process.** Correct in 2026-09-08's code and
the reason D3 said what it said. Rejected because the fork removed the premise:
`GetForecastRequest` now carries the filter and the response reports the area
back, so a pair per organisation buys isolation that a request field and an
equality check already buy — at the cost of a generated compose file, a service
per tenant, and a name that has to be derived identically in two places forever.

**Trust the area filter and skip the `meta.area` check.** The filter is applied
by the reader and it fails closed, so the check should never fire. Rejected for
the same reason a marker is written after the bytes: the whole boundary is now a
Django query plus one request field, and a boundary with nothing verifying it is
a boundary nobody will notice losing. It costs a dictionary lookup.

**403 for a model the caller may not see.** More informative, and wrong: it
confirms the model exists. `visible_to`'s doctrine across this instance is
absence, and D18 restates it for exactly this route.

**Derive visibility from the collection and drop the field.** Simpler, and
already refused by D18: an NMHS may reasonably serve maps publicly and point
forecasts to members only, which deriving cannot express in either direction.

**Cache in Django rather than at the proxy.** Rejected for the reason ADR 0029
gives: the point of caching a hot public endpoint is that the hit never reaches
the application.

**Pass the upstream 404 through.** One fewer mapping, and it tells the caller
something plausible. Rejected because what it tells them is false: their
coordinates are probably fine and the model is not loaded. The route would be
reporting an instance fault as a caller error, which is precisely the state
nobody investigates.

## Consequences

- **The tenant boundary is a Django query, verified on every response.** That
  catches a *view* bug. It does **not** catch a publisher bug that wrote one
  organisation's data under another's area key — that passes the equality check
  silently, and saying so is part of what D14 gives up.

- **A model cannot be renamed once published**, and the route is why it matters
  twice over: the slug is a segment of every storage key *and* the name a
  consumer's client has hard-coded.

- **The first throttle on the instance sets a precedent.** `DEFAULT_THROTTLE_CLASSES`
  is deliberately still unset — a default would apply silently to every existing
  API view — so a second route that wants throttling opts in the same way.

- **Nothing in core mentions Forti.** The view, the route, the throttle, the
  timeout, the upstream's name and the cache lifetime are all here, each read
  with `getattr(settings, "GEORIVA_FORTI_…", <plugin default>)`. An operator can
  still set any of them in core's settings file; core simply does not ship one.

- **An unpublished model is invisible rather than pending.** Creating a
  publication changes nothing a consumer can see until its first publish
  succeeds, which is the same rule `rdfconfig.servable` applies to the area list
  and for the same reason.

- **The `/api/` cache zone finally has an occupant**, and it is one route's
  successful public responses. An operator watching the zone fill is watching
  this and nothing else.
