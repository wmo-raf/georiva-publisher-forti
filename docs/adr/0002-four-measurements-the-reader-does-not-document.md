# Four measurements the reader does not document

## Status

accepted

The record of what M5's first serving plane cost to find. Three of the four are
already implemented — two in `serving.py`, one in core's nginx — and the fourth
is a number in `rdfconfig.py`. **This ADR changes nothing.** It exists because the
measurements were bought with a running system and a day, and the code that
embodies them is not where anybody goes looking for *why*.

Carries the measurements out of core's withdrawn `docs/adr/0028-a-serving-pair-per-organisation.md`,
which exists only on the abandoned branch `feat/forti-serving` (`bc94464`). ADR
0001 supersedes that document's *design*; this one keeps its facts. The number
0028 in core now belongs to core's plugin URL hook.

Implements nothing. Constrains D14, D17 and D19 by saying what the reader
actually does.

## Context

The first serving plane shipped and ran on 2026-09-09: one `rawdataforecaster` +
`jsonfrontend` pair per organisation, generated by `manage.py
generate_forti_compose`, a Django view in `georiva.api`, the instance's first DRF
throttle, an nginx cache zone. It was verified live — `/api/forecast/?lat=-1.2864&lon=36.8172`
returned locationforecast 2.0 for Nairobi with 13 timesteps, 11 units, day/night
symbols and 6- and 12-hour summaries.

It is superseded, for the reasons ADR 0001 gives. What it paid for is not.

Each of the four below was found by running the thing, and each one is the kind
of fact that a reader of the code would otherwise have to rediscover the same
way. Three share a shape: **the failure is silent, and silent in the direction
that looks like success.** That is why they are worth an ADR rather than a
comment.

## Decision

### 1. Switch on whether the body parses, never on `Content-Type`

`jsonfrontend` sets no content type on a successful response, so Go's `http`
sniffing stamps `text/plain; charset=utf-8` over a perfectly good
locationforecast document.

A view that trusts the header therefore sends **every real forecast** down its
error branch, and every error down it too — so it never returns a forecast and
never reports anything unusual. The unit tests missed it because the fake set the
header the view expected, which is the general hazard: a fake built from the
view's assumptions cannot contradict them.

The distinction that works is the body. `jsonfrontend`'s own failures are
`http.Error` prose and do not parse; its successes are JSON and do. `serving.py`
switches on the status code and on whether the body parses, and says so where it
does.

### 2. `maximum_gridpoint_distance` is a great-circle distance in metres

Probed south of the M0 area's edge (1920 points, 0.25° spacing, lat −5.49..6.24 /
lon 33.05..42.80), coverage ends at **50.1 km** against a configured `50000`. A
true great-circle distance from the nearest gridpoint, accurate to the metre —
not a cell count, not a bounding-box margin.

That bounds the choice from below. The worst-case *interior* point is a cell
centre, √2/2 × 0.25° ≈ **19.7 km** from its nearest gridpoint, so anything under
about 20 km punches holes **inside** the domain — and a hole inside a domain
reads to a caller exactly like being outside it.

Settled at 50 000 m (`rdfconfig.DEFAULT_MAXIMUM_GRIDPOINT_DISTANCE`): safe
against the interior worst case, and buying roughly 1.8 cells beyond a bbox edge.
How far outside a published domain the service should answer at all is policy,
and the measurement is what makes it a policy question rather than a guess.

It is process-wide and cold — one value for every model on the instance, changed
only by a restart. That is one of the things D14 explicitly gives up, and it is
wrong the day somebody publishes a 3 km domain wanting a tighter radius.

### 3. The upstream 404 has exactly one meaning, and did not before

With `geographic_extent: null` — which is what this publisher writes, because a
non-null one is what the GEOS polygon leak needs — `WithinGeographicArea`
(`dataset.go:196`) is unconditionally true. Under the old design "outside
coverage" could therefore only arrive as a **200 with a GeoJSON error body**, and
the 404 branch was unreachable.

Under D14 a request always names its area, so `bestArea` fails closed and returns
`ErrOutsideAllGrids` before any geographic test. The 404 became reachable, and it
now means one thing: **the named area is not loaded.**

That is not a caller error. The caller's coordinates are probably fine; the
instance is serving a model whose bytes `rawdataforecaster` does not hold — a row
whose `published_version` is set under a layout whose objects are not on the
bucket, which is precisely the state M5.9 existed to clear. `serving.py` maps it
to **503** and logs the area, because passing it through would report an instance
fault as a caller error, and nobody investigates those.

The 200-with-an-error-body branch did not go away and is still the answer for a
point that is genuinely too far from every gridpoint of a **loaded** area. The
two are now distinguishable, which is the whole of this finding.

### 4. A cache key over `/api/` must include `$host`

`/api/forecast/{model}/?lat=&lon=` is byte-identical across organisations, and
both pre-existing nginx zones key on `$request_uri` alone. Under D19 this stops
being a forti fact and becomes the instance's `/api/` rule —
`proxy_cache_key "$host$request_uri"` (`deploy/nginx/nginx.conf:266`).

It matters more under D14 than it did before. One shared pair really does return
different bodies for the same URI on different hosts: the model a host may see is
a Django query over the host's organisation, so `ecmwf-ifs` is a forecast on one
host and a 404 on the next. A key without `$host` would serve the first
organisation's forecast to the second, out of cache, with nothing in the
application to notice.

## What the cutover verified — 2026-09-13

The evidence is kept here rather than in a commit message because three of the
four findings above are re-observed by this one run, and a measurement is worth
more beside the thing it measures.

One pair, one area, `central.ecmwf-ifs`, published at version `178925760000`
(run 2026-09-13T00:00Z) — 1920 points, grid `dd566ea71ba587cecb5d66213e235d07`,
13 parameters, **12 steps**. Twelve rather than the sixteen of the earlier
publish because twelve is what the collection holds: the four earliest steps'
valid times have passed and are no longer in the index. The republish wrote what
was there.

**The four hops agree, on both documents.** `verification.report()` — the panel's
own reader — puts `intended`, `bucket`, `volume` and `loaded` on one sha for
`rawdataforecaster.json` (`0aa2e5d51916…`) and one for `jsonformat.json`
(`107ab39f7304…`), each hop `present` and agreeing with hop 1. The area row reads
`published = available = loaded = 178925760000`: M5.1's `AreaStatus`, reporting a
version rather than a Go map miss that would read as `0`.

**A real forecast**, `GET /api/forecast/ecmwf-ifs/?lat=-1.2864&lon=36.8172` on
host `localhost`: 200, 12 timesteps from 2026-09-13T12:00Z to 2026-09-14T21:00Z,
11 units, `next_6_hours` on 10 steps and `next_12_hours` on 8, symbols including
`partlycloudy_day`, `partlycloudy_night`, `fair_day` and `fair_night` — the
day/night bit from solar elevation — and `Cache-Control: public, max-age=1800`.
`properties.meta.area` came back `central.ecmwf-ifs`, which is the equality check
D16 requires passing on live data rather than on a fake.

That response is finding 1 in the affirmative: the body parsed, and it is what
the view returned.

**The 404 means what finding 3 says.** `GET /api/forecast/ecmwf-ifs/` at Accra
(5.6, −0.19), some 3 800 km outside the domain, returns **200** carrying
`properties.meta.error: "no data at the given location"`, no units and an empty
`timeseries` — not a 404. The 404 stayed reserved for an area that is not loaded, which is what makes
it actionable.

**Finding 4, demonstrated by three hosts.** A second identical request on
`localhost` is `X-Cache-Status: HIT`. The same URI on `emi.localhost` and
`ke-kmd.localhost` returns **404** with an empty listing, and is *not* served the
cached body. Without `$host` in the key it would have been.

`GET /api/forecast/kenya/` — the name the row published under until this
cutover — is a 404 on every host.

Finding 2 is not re-measured here. It costs a staged probe grid and the number it
produced has not moved; this run's `maximum_gridpoint_distance` is the 50 000 the
finding settled on, and Accra's answer is consistent with it.

### The remap, both ways

The part only ADR 0003 could make observable. The `10fg` slot was remapped to

### Three things the re-run showed that the plan did not say

- **The panel's `differs` window is the status sync, not the reader.** The reader
  held the new version two seconds after the publish; the panel saw it within a
  minute (45 s on the remap, about 50 on the revert), because it reads the
  bucket's copy of the reader's status document, which the sidecar uploads once
  per `FORTI_SYNC_INTERVAL`. The verdict
  on that window says "Wait for the next refresh (up to 5 minutes)". Five minutes
  is the configuration reconciler's interval, not this path's; the honest bound
  here is the 3-second poll plus one sync pass. The sentence errs long, which is
  the safe direction, but it names the wrong mechanism.
- **A fresh start reports its predecessor's status, and says so.** The first panel
  read after the pair came up was taken before the sidecar's second pass, so the
  bucket still held status documents ten days old. The panel rendered their age
  as "10 days ago" and called the area `differs`, rather than reporting health.
  One sync pass later it agreed.
- **The compose file's default sidecar image had stopped existing.**
  `minio/mc:RELEASE.2025-08-13T08-35-41Z` was not found at pull, and the `minio/mc`
  repository is gone from Docker Hub entirely. Core moved its object store to Silo
  (`b6dd116`), pinned at `pgsty/silo:RELEASE.2026-09-16T00-00-00Z`. The default is
  now `pgsty/mc` at that same release tag, which carries `sh`, `sha256sum`, `cut`
  and `date` and, like the image it replaces, no `cmp`. A daemon with the old
  image already cached still runs it; any host pulling the old default fresh gets
  "not found".

## One correction to D23

D23 in the plan says a second writer to the config "would be silently reverted
within 60 s". **60 s is `FORTI_SYNC_INTERVAL`**, the sidecar's pass — how stale
the bucket's copy of a *status* document may be. It is not what reverts a writer.

What reverts a writer is D22's reconciler: `refresh_forti_config` rebuilds both
documents from the database every **five minutes** and uploads whichever differs.
The plan is the agreement and was left as written; the code and the README say
"one reconciler tick", and this is where the two are reconciled.

The distinction matters in the direction that would bite. Somebody reading "60 s"
and watching a hand-edited config survive for four minutes would conclude the
reconciler is broken, and go looking.

## Alternatives considered

**Leave the findings as comments where they are implemented.** They already are,
and that is not the objection: a comment answers "why is this line like this" for
a reader who is already on the line. None of these four is discoverable from the
line. The `Content-Type` rule is a *negative* — the absence of a header check —
and nothing marks the place where a check is not.

**Put them in the README.** The README says how to run and verify this plugin.
These are facts about somebody else's program, three of which are only
interesting to whoever changes the code next.

**Fold them into ADR 0001.** 0001 decides the serving plane's shape and is
already long. These constrain that shape without being part of it, and their
provenance is a design that 0001 supersedes — mixing the two would make 0001
argue for a design and cite the abandoned one as evidence in the same breath.

**Re-measure finding 2 during the cutover.** It needs a probe grid staged for the
purpose and a bisection south of the domain edge. The number has not moved, the
configured value is unchanged, and a measurement repeated to feel thorough is a
day spent confirming what is already written down.

## Consequences

- **Three rules in the code now have a citable reason.** `serving.py`'s parse
  test and its 404 → 503 mapping, and `rdfconfig`'s 50 000. A change to any of
  them reads as a change to a decision rather than as tidying.

- **The `Content-Type` trap outlives this plugin.** Anything else that proxies
  `jsonfrontend` — a second frontend, a cache warmer, a health probe — meets it,
  and it now has a name.

- **The `$host` rule is core's, not this plugin's.** It is in core's nginx and in
  core's ADR 0029, and a second `/api/` route inherits it without knowing Forti
  exists. If it is ever narrowed back to `$request_uri`, this plugin is where the
  breakage shows first and worst.

- **Finding 2 bounds a policy question it does not answer.** How far beyond a
  published bbox to answer at all is still a choice, and the day a 3 km domain
  arrives the process-wide value is the thing that has to give.

- **The cutover's evidence has a home.** The next person to ask "did this ever
  actually serve" has a date, a version, a sha and a coordinate, rather than a
  commit message to search for.
